Setting the clock back loses a price and mixes up the history
may be a bug

      
The full write-up, and how to run it yourself


      
The idea first. A versioned table is like a price notebook. Each line says: "this price, from this date, until this date". For any day you pick, exactly one line should be true. The server writes the dates itself, using its clock. But MariaDB lets a session move its own clock, for example to replay old changes. If the clock goes back, the notebook breaks. Follow the story.

What "overlap" means

          
Two lines of the notebook cover the same days. After step 4, the line "11.00 from 2020" lies on top of "10.00 until mid-2021" and on top of "12.50 until 2024". In the picture, the red zones are the days with two prices.

        

        

          
Why it is a problem

          
    
            
  • A real price is deleted. 14.00 was the price from January 2024 on, and now no line remembers it.
    • 
            
  • Some days have two answers. Ask for June 2020 and you get 10.00 and 11.00.
    • 
            
  • Some days get a different answer. Ask for 2025 and you get 11.00. Before step 4 the notebook said 14.00, and that line is gone.
    • 
            
  • Nobody is told. No error and no warning. An invoice, a report or an audit built on this history is wrong and nobody knows.
    • 
          

        

        

          
How to avoid it, and how MariaDB could fix it

          
    
            
  • In this project: the clock is never moved. The load writes the real dates directly (system_versioning_insert_history), so this cannot happen.
    • 
            
  • On a real server: load the history first, then turn on secure_timestamp=YES. After that, no session can move its clock any more (error 1290). "Load first, lock after."
    • 
            
  • The fix to ask MariaDB for: refuse the UPDATE when its time is before the start of the line it closes. The server already refuses a line that ends before it starts when you insert it by hand. It should do the same here.
    • 
          

        

      


      

        
How to say it in one sentence

        
"If a session sets its clock back to before the last change, MariaDB accepts the UPDATE, silently drops the current version, and the new version overlaps older ones, so one date can return two prices."

An old date reads almost the whole history
optimizer idea

      
The full write-up, and how to run it yourself


      
The idea first. Every time an article changes, MariaDB keeps the old version as a line: "this text, from this date, until this date". It stores the lines of one article sorted by the "until" date. When you ask "what did the article look like on a date?", the right line is the one where from ≤ date < until. The problem is how many lines MariaDB reads to find it. Try it on a small article with 10 versions.

    Pick a date, then press a button.
    
      
    

      
    
        
    
          
    Why AS OF reads so much
    
          
      
            
    • Because the lines are sorted by "until", MariaDB can jump straight to the first line that ends after your date. Everything before it is skipped. That part is fast.
      • 
            
    • But it also has to check "from ≤ date", and it does not know that the lines follow each other without overlapping. So it keeps reading every line until the end, just in case another one also matches. It finds only one.
      • 
            
    • An old date means almost every line ended after it. So an old date reads almost the whole history. A recent date reads only a few lines.
      • 
          
    
        
    
        
    
          
    Why one line is enough
    
          
    In a versioned table each version ends exactly when the next one starts. So the first line that ends after your date is always the answer. The first-row query asks for exactly that: sort by "until", take the first line after the date, stop.
    
          -- AS OF: reads every line that ends after the date
SELECT rev_id FROM article
  FOR SYSTEM_TIME AS OF TIMESTAMP '2005-06-01'
  WHERE page_id = 57400;

-- first-row query: reads one line
SELECT rev_id FROM (
  SELECT rev_id, row_start FROM article FOR SYSTEM_TIME ALL
  WHERE page_id = 57400 AND row_end > '2005-06-01'
  ORDER BY row_end LIMIT 1) v
WHERE v.row_start <= '2005-06-01';
          
    The last line checks that the article already existed on that date. Same answer as AS OF, tested on 220 dates (check 22).

    Why it matters
    
          
    It grows with the history. On a test key with 1,000,000 versions, AS OF on an old date took about 750 ms. The first-row query took under 2 ms. We also added an index on "from"; MariaDB still chose to read everything, about 20 times slower than with the index.
    
        
    
        
    
          
    The idea for MariaDB
    
          
    The optimizer is the part of MariaDB that decides how to read the data. In a versioned table the server writes the versions itself, one after the other, so for one key they never overlap. When the query gives the whole key (one article), the optimizer could stop at the first line, like our query does. Then every date would cost one line. This was asked at the meeting with MariaDB on 5 November 2026.
    
          
    The catch: imported history can overlap (see the clock finding above), and then one line is not enough. That is why check 21 makes sure the versions of each article never overlap.
    
        
    
      
    

      
    
        
    How to say it in one sentence
    
        
    "For one article, AS OF reads every version that ended after the date you ask for, so an old date reads almost the whole history. Since versions never overlap, the first of those rows is already the answer, and reading only that row gives the same result."

    OPTIMIZE TABLE fails but says it worked
    may be a bug
    
      
    The full write-up, and how to run it yourself
    
      
    In plain words. After you delete old history, the space only comes back when the table is rebuilt. OPTIMIZE TABLE on a versioned table refuses to do it. The refusal is hidden in the result rows, and the statement still reports success. A cleanup script would think it freed the space.

    Five gaps in the documentation
    documentation
    
      
    Written up in finding 5, finding 6 and finding 7.
    
      
    
        
    Importing history
    The docs give it one line. Our five-step tutorial and six-row example can be lifted as they are.
    
        
    Overlaps on import
    Two versions that cover the same months are both accepted, and a date between them returns two rows for one key. Nothing checks this.
    
        
    Who can write a past
    On a default server, a user with only INSERT and UPDATE could add a version dated 2015 and one dated 2030. Only secure_timestamp=YES stops it, and it also stops any import. So: load first, lock after.
    
        
    The 1970 floor
    History cannot start before 1970. The error says "incorrect datetime value" and not why.
    
        
    The overlap error
    "Duplicate entry 'TRK-12-2026-03-25-2026-03-20'" prints the end of the period before its start, and calls an overlap a duplicate.
